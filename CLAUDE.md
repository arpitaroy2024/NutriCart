# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

NutriCart is a native Android app ("Smart grocery, healthier you"), built with Kotlin and Jetpack Compose. The entry flow, local storage, profile setup, Home, Profile, the bottom-navigation shell, grocery generation, the generated list, list editing, nutrition analysis and the allergy and health-condition review are built.

- Package / namespace: `com.example.nutricart`
- Single Gradle module: `app`
- Min SDK 24, target/compile SDK 37
- Kotlin 2.2.10, AGP 9.3.1, Compose BOM 2026.02.01

## Commands

All commands are run from the repo root using the Gradle wrapper.

```
./gradlew assembleDebug          # build debug APK
./gradlew installDebug           # build and install on a connected device/emulator
./gradlew test                   # run local JVM unit tests (app/src/test)
./gradlew connectedAndroidTest   # run instrumented tests on a device/emulator (app/src/androidTest)
./gradlew test --tests "com.example.nutricart.ExampleUnitTest"   # run a single unit test class
./gradlew lint                   # run Android Lint
```

On Windows use `gradlew.bat` instead of `./gradlew`.

## Architecture

- The app is being built in phases against `project_docs/implementation_plan.md`, which summarises the two requirement PDFs in `project_docs/`. Read the plan before adding screens; the PDFs are the source of truth for UI, dimensions and navigation. Phases 0 to 8 are done (see the `phase_*.md` files in `project_docs/`). Keep to the phase being built. From Phase 4 on the PDFs are the functional reference, not a pixel spec: improve the UI where justified and record each deviation (PDF / suggestion / decision) in the phase document.
- `MainActivity` hosts `NutriCartTheme { NutriCartNavHost() }`. Navigation uses Navigation Compose: route strings are in `navigation/Routes.kt` and destinations are registered in `navigation/NutriCartNavHost.kt`. Built destinations: splash, welcome (onboarding), login, register, profile/setup (also `?mode=edit`), home, generate, list (the List tab, latest list), list/{listId} (pushed after generation), list/{listId}/edit, list/{listId}/add, nutrition (the Nutrition tab, latest list), nutrition/{listId} (pushed from a list), alerts/{listId} (the profile review of one list) and profile. The bottom bar is drawn by a `Scaffold` around the `NavHost` and shown only on the four tab roots (`navigation/ShellTabs.kt`); tab screens therefore apply `statusBarsPadding()` only, while full-screen destinations handle all system bars themselves.
- `navigation/EntryRouter.kt` holds the routing decisions (onboarding flag, session, stale session, profile). The splash and both auth screens use it; do not duplicate that logic in screens.
- Screens live in `ui/screens/<feature>/` as a `…Screen.kt` (a stateful wrapper plus a private stateless `…Content` with a preview) and a `…ViewModel.kt` exposing one `StateFlow` of UI state. ViewModels are created with `viewModel(factory = AppViewModelFactory)` (`ui/AppViewModelFactory.kt`); add an initializer there for each new ViewModel.
- User-visible text goes in `res/values/strings.xml`. Onboarding panes 2 and 3 are provisional copy awaiting approval. Login and Create account are project requirements that are not in the PDFs.
- Reusable components (C-01 to C-13 from the PDF, plus top bar, logo, progress ring, empty state) are in `ui/components/`; build screens from these rather than raw Material components. `ComponentPreviews.kt` shows them all.
- Design tokens are in `ui/theme/`: read colours from `NutriCartTheme.colors` and text styles from `NutriCartTheme.typography`, and use `Spacing`, `Sizes`, `NutriCartShapes`, `Elevation` and `Motion` from `Dimens.kt`, rather than hard-coding values. Dynamic colour is off.
- Every user flow is local: no screen makes a network call, except the list screen's optional AI insights when the user asks for them. Data lives in Room (`data/local/`) and a Preferences DataStore (`data/SettingsStore.kt`, holding the onboarding flag and the logged-in account id). Screens should go through the repositories in `data/repository/`, obtained from `(application as NutriCartApp).container` (`AppContainer`, manual DI, no Hilt). Repositories for user-owned data read the account from the session and never take an account id from the caller.
- The Room database is at version 3. Any schema change needs a new version and a `Migration` added to `ALL_MIGRATIONS` in `NutriCartDatabase.kt`, plus cases in `data/local/MigrationTest.kt`; never use a destructive fallback. A profile holds a set of listed allergies, a set of listed health conditions, and a list of custom (typed) values for each, stored as JSON arrays; no conditions of either kind means none. Custom values are cleaned by `ProfileRepository.cleanCustomEntries` (trimmed, no repeats ignoring case, 40 characters, 10 entries); the enum constant names in `data/model/Models.kt` are what is stored, so do not rename them.
- Passwords are stored only as salted PBKDF2 hashes (`data/auth/PasswordHasher.kt`). Catalog items and prices are demo seed data (`data/local/SeedData.kt`); a price with `updatedAt == null` is a demo price and must not be shown as a real or recently updated one.
- `domain/GroceryGenerator.kt` builds the list. It is a pure, deterministic, on-device rule set, not an AI model, and must stay free of Android, database and UI code; no user flow makes a network or LLM call (see the Phase 9 note below). Its basket template is demo data beside the catalog seed. It leaves out items the catalog states contain a listed allergen, and items a documented health-condition rule flags for a listed condition (`domain/ProfileConflicts.kt`, which uses the same `HealthConditionAnalyzer` as the review so the two cannot disagree); a condition without a rule leaves nothing out, and the catalog's `flaggedConditions` tags are not read. That is not a safety check.
- The allergy and health-condition review lives in `domain/conflicts/`: `AllergyMatcher` (profile allergies against the catalog's stated `allergens` only, never item names; typed allergies match only through the explicit table in `CustomAllergenAliases`), `HealthConditionAnalyzer` (rules are data in `HealthRules`; add a rule only when the catalog holds the figure it needs), `AlternativeFinder` and the coordinator `ConflictAnalyzer`, which returns a structured `ConflictAnalysis`. Screens call it through `ui/screens/alerts/ProfileReview` and recompute from the current list and profile; nothing derived is stored. Only Celiac, Diabetes, Prediabetes and Anemia have rules; every other condition, and every typed condition, is reported as not checked. The catalog's `flaggedConditions` demo tags are not evidence and must not be used here. "Keep anyway" is the per-item `alertOverridden` flag: the concern stays in the analysis. Wording must never say safe, unsafe or give medical advice (`ui/ProfileReviewTest` scans the strings). Details: `project_docs/phase_8_allergy_health.md`.
- Nutrition lives in `domain/nutrition/` as three separate pure parts run in order by `NutritionAnalyzer`: `NutritionCalculator` (per-100 g catalog values x quantity x `gramsPerUnit`), `NutritionScorer` (the 0-100 score: 60% adequacy, 25% macronutrient balance, 15% food-group variety) and `NutritionInsights` (structured observations the screen turns into sentences). Reference values are in `NutritionReference`. Nothing derived is stored: screens recompute from the list's items and the profile's household size, so list edits show at once. The score is a NutriCart product heuristic, not a clinical measure; this code must not read the profile's allergies or conditions and its wording must make no medical, "safe" or "unsafe" claims (`ui/NutritionScreenTest` checks the strings). Details and formula: `project_docs/phase_7_nutrition.md`.
- Phase 10 added the one user-facing use of the AI layer: optional "AI insights" on the grocery list screen (`ui/screens/grocerylist/AiInsights.kt`, `AiInsightsCard.kt`, `GroceryListViewModel.onRequestInsights`). The ViewModel depends on `AiReasoningEngine` only and gets it from `AppViewModelFactory`; `AiInsightsContext` builds the sanitized context (no name, email, ids, region or unit prices) from the list, the profile, `NutritionAnalyzer` and the profile review. The answer is advisory text held in UI state only: it is never stored, never changes the list, review or nutrition figures, and is dropped when the list or profile changes. A request is sent only when the user taps the button, and every failure is a friendly state with Try again. Only `ui/screens/grocerylist/` may name `domain.ai`. Details: `project_docs/phase_10_ai_insights.md`.
- Phase 9 added the AI reasoning layer. `domain/ai/` holds the provider-neutral `AiReasoningEngine`, request, response and `AiResponseValidator`, and must stay free of Firebase and of `data/`. `data/ai/` holds `AiJson.kt` (prompt, schema, parser), `AiModels.kt` (the only place a model is named) and two provider paths. The app's path (Phase 9B) is `data/ai/firebase/`: `FirebaseAiReasoningEngine` (no Firebase imports; talks to an `AiTextGateway`) and `FirebaseAiLogicGateway`, the only file that may use the Firebase SDK; it is exposed as `AppContainer.aiReasoningEngine`, created lazily, and nothing may touch Firebase at app start. The App Check provider comes from the build type (`src/debug`: debug provider, `src/release`: Play Integrity). The Phase 9A path (`GeminiAiDataSource` / `GeminiAiRepository`, REST with a developer key) is development-only and used solely by `GeminiLiveCheck` in the test source set when `NUTRICART_AI_LIVE=1`. Every model answer must go through `AiResponseJson.parse`; the engine returns `AiResult.Failure` instead of throwing. Never put an API key in source, `BuildConfig`, resources or `local.properties`; Firebase AI Logic needs no Gemini key in the app. `app/google-services.json` is git-ignored and the google-services plugin is applied only when it exists; without it the engine returns `NotConfigured`. The Firebase libraries give the app `INTERNET`; `RECORD_AUDIO` is removed in the manifest. The model sits above the deterministic code and is never the source of truth for prices, allergens, nutrition figures, medical facts or the catalog; outside the `ai` packages only `AppContainer` may name `data/ai`, and only the list screen's package may name `domain/ai` (`data/ai/AiFoundationTest` and `data/ai/firebase/FirebaseAiLayerTest` check these rules). Details: `project_docs/phase_9_ai_foundation.md` and `project_docs/phase_9b_firebase_ai_logic.md`.
- List edits are saved as they are made (no draft, no Save step) through the single-edit operations on `GroceryListRepository`; screens observe the list as a Flow. The editor and item picker always work on the list id in their route, never "the latest list". A list never holds the same catalog item twice (adding again raises the quantity), quantities stay within `domain/ListRules`, and going over budget is allowed and shown, never blocked or corrected. Use `domain/ListTotals` and `ui/screens/grocerylist/BudgetSummary` for budget figures.
- Unit tests in `app/src/test` use Robolectric (pinned to SDK 35 in `src/test/resources/robolectric.properties`) with a real in-memory Room database; see `data/TestEnvironment.kt`. `ui/AppShellNavigationTest.kt` drives the real nav graph and screens with the Compose test rule; its waits must pump the main looper (see `waitFor` there). `app/src/androidTest` holds the template instrumented test and `FirebaseAiLiveCheck`, an opt-in device check that is skipped unless `nutricartAiLive=1` is passed.
